# CLAUDE.md — проект «Клюёт»

## О проекте

«Клюёт» — мобильное приложение для рыбаков в России.

Основная идея:
- карта мест для рыбалки;
- пользовательские отметки о местах;
- информация о том, какая рыба встречается и клюёт;
- свежие отчёты пользователей;
- рейтинг мест;
- разделение мест на дикие бесплатные и платные;
- информация о доступе к месту, подъезде, береговой или лодочной рыбалке;
- со временем — пользовательская база актуальных рыболовных мест по всей России.

Продукт ориентирован на рыбаков по всей России. Архитектура, карта, поиск, фильтры и модель данных не должны быть привязаны к одному региону. При этом наполнение базы и запуск могут происходить поэтапно, начиная с регионов, где можно обеспечить достаточную плотность актуальных данных.

Главная ценность продукта:
помочь рыбаку быстро понять, **куда поехать, что там можно поймать и насколько актуальна информация о месте сейчас**.

## Пользователь

Основной пользователь — рыбак в России.

При исследовании учитывай реальные особенности аудитории:

- рыбаки не всегда готовы публиковать хорошие места;
- информация о клёве быстро устаревает;
- место может быть доступно только в определённый сезон;
- важны подъезд, парковка, берег, лодка и состояние дороги;
- важны ограничения на ловлю;
- важны виды рыбы;
- часть пользователей может намеренно скрывать точные координаты;
- привычными альтернативами являются знакомые рыбаки, Telegram, форумы, группы VK, карты и поиск.

## Принципы продукта

### 1. Актуальность важнее количества данных

Лучше мало свежей информации, чем большая база устаревших отчётов.

### 2. Карта — основной интерфейс

Место рыбалки должно рассматриваться прежде всего как географическая точка.

### 3. Пользовательский контент должен приносить пользу

Не добавлять социальные функции только ради активности.

Каждый элемент пользовательского контента должен помогать ответить на вопрос:

**стоит ли ехать сюда на рыбалку?**

### 4. MVP должен быть маленьким

Не добавлять функцию только потому, что она может понадобиться в будущем.

Для каждой новой функции задавать вопросы:

- нужна ли она для первого пользовательского сценария;
- можно ли проверить гипотезу без неё;
- увеличивает ли она сложность продукта;
- есть ли более простой вариант.

### 5. Не копировать конкурентов механически

При анализе конкурентов фиксировать:

- какую проблему решает функция;
- насколько хорошо она работает;
- нужна ли она пользователям «Клюёт»;
- можно ли решить эту задачу проще.

## Основной пользовательский сценарий

Базовый сценарий MVP:

1. Пользователь открывает карту.
2. Видит места для рыбалки.
3. Выбирает место.
4. Видит:
   - какие виды рыбы там ловят;
   - насколько свежие данные;
   - последние отчёты;
   - тип места;
   - условия доступа.
5. Принимает решение, стоит ли туда ехать.
6. После рыбалки может оставить короткий отчёт.

## Работа с источниками

При исследованиях:

- преимущественно использовать российские источники;
- указывать прямые ссылки;
- не выдавать предположения за факты;
- отделять факты от собственных выводов;
- проверять дату материала;
- учитывать, что старые данные о рыбалке могут быть неактуальными;
- не делать вывод на основании одного источника, если можно проверить несколько.

Зарубежные сервисы использовать только для изучения интересных продуктовых механик.

## Важный вопрос

При любом продуктовом решении помнить главный вопрос:

**Почему рыбак откроет «Клюёт», а не Яндекс Карты, Telegram, форум или просто спросит знакомого рыбака?**

Если функция не помогает ответить на этот вопрос — вероятно, она не является приоритетной.

## Источники UI и порядок работы

Источники истины разделены по области ответственности:

- **Figma K-DS** — библиотека UI-компонентов, их вариантов, состояний, размеров и токенов: https://www.figma.com/design/AdQjv6kqqQG7IMjOAiW62k/K-DS?node-id=68-307
- **Figma K** — актуальные утверждённые продуктовые макеты и их компоновка: https://www.figma.com/design/WIFYiVA2QFFcDn0YYA1CCq/K
- **`docs/`** — утверждённая продуктовая логика и пользовательские сценарии.
- **HTML-прототип `prototype-mobile/`** — исключительно вспомогательный источник работающей логики, не противоречащей `docs/`. Он не переопределяет K-DS, K или `docs/` и не является источником визуальных решений.

**Постоянное обязательное правило:** запрещено использовать `prototype-mobile/` (HTML-прототип) для сравнения, копирования и реализации UI-компонентов, SVG-иконок, размеров, отступов, цветов, токенов, состояний и визуальных стилей. Читать HTML-прототип разрешено только для указанной выше работающей логики. Визуальные решения брать из K-DS, а актуальную компоновку продуктовых экранов — из K.

Перед любой реализацией или изменением UI обязательно:

1. Изучить подходящие компоненты в K-DS: варианты, состояния, размеры, токены и вложенные компоненты.
2. Сопоставить их с использованием на утверждённых экранах K и с логикой и сценариями в `docs/`.
3. Только после этого переходить к реализации в коде.

Библиотека K-DS пока не полностью упорядочена. Искать подходящие компоненты по названиям, структуре страниц и слоёв, а также по их фактическому использованию в макете K. Не считать найденный дубль актуальным без проверки его связи с используемыми компонентами и утверждёнными экранами.

Не выдумывать неопределённые значения, размеры, токены, варианты или состояния. Если нужный компонент или токен отсутствует либо неоднозначен в K-DS, параметр не найден, источник недоступен, актуальность дублей не подтверждена либо между источниками есть конфликт — остановить реализацию затронутой части UI, сообщить Дмитрию, указать конкретные источники и расхождения и запросить решение. Не выдумывать замену и не разрешать такие конфликты самостоятельно.

Figma использовать только для чтения: не менять файлы K-DS и K, их компоненты, экраны, токены, структуру или названия.

Соблюдать UX-контракт этого документа; правила переходов здесь не дублировать. Не подменять UX-контракт универсальным выбором одного метода Expo Router.
