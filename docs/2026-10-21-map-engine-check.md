## 1. Рекомендованный движок: `react-native-maps` (последняя 1.29.11)

| Критерий | react-native-maps | expo-maps | react-native-map-clustering |
|---|---|---|---|
| Expo Go | ✅ подтверждено Expo docs («compatible with Android, iOS, and Expo Go», «no additional setup») | ⚠️ не подтверждено | работает, но примеры на SDK 35 |
| Apple Maps на iOS без ключей | ✅ MapKit по умолчанию | ✅ | — |
| Кастомные маркеры из K-DS | ✅ любые RN-вьюхи в детях `<Marker>` | ❌ только иконки через `useImage` — дети не поддерживаются | через renderCluster |
| Слои (OSM-тайлы) | ✅ `UrlTile` `/{x}/{y}/{z}` | ❌ API не виден | — |
| Активность | обновлён 27.09.2026 | beta-статус | последняя публикация 23.07.2025 — риск |

Обоснование: единственный вариант, который одновременно даёт Apple Maps, кастомные маркеры любых вьюх (нужно для пинов и трёх вариантов кластеров K-DS) и подтверждённую работу в Expo Go — текущем рабочем цикле проекта.

Отклонённые альтернативы:

- **expo-maps** — API на данных (`markers`, `annotations` — массивы объектов), а не на React-компонентах: K-DS-маркер как вьюху туда не встроить; кластеризации в API нет.
- **Mapbox/MapLibre** — требуют кастомную нативную сборку, не работают в Expo Go; стилизация нужна не настолько, чтобы терять Expo Go.
- **react-native-map-clustering** — оболочка над supercluster, слабо поддерживается; для трёх утверждённых вариантов кластеров всё равно нужен свой `renderCluster`. Проще взять supercluster напрямую.

## 2. Подтверждённые возможности (документацией Context7)

1. **Совместимость.** Плагин требует rnmaps ≥ 1.22 и Expo SDK ≥ 53 (`docs/installation.md`). Пир-веса 1.29.11: `react ≥ 18.3.1`, `react-native ≥ 0.76` — наши react 19.2.3 / RN 0.86.3 проходят по диапазону. Конфиг `app.json` в проекте есть — плагин добавится туда.
2. **Apple Maps на iOS + Expo Go.** `provider` не задан → MapKit на iOS, без API-ключа. На Android rnmaps всегда Google Maps (ключ нужен для релиза, для Expo Go — нет).
3. **Кастомные маркеры.** Дети `<Marker>` — произвольные RN-вьюхи; для производительности — `tracksViewChanges={false}` с перерисовкой по требованию (документировано).
4. **Приблизительная область ~1 км.** `Circle` принимает `radius` в метрах и масштабируется географически. Пунктир границы: `lineDashPattern` у `Circle` — **iOS only**. Свойства тапа у `Circle` в API не найдено.
5. **Тап по области.** `Polygon.onPress` поддержан на iOS и Android (исходники `MapPolygon.tsx`); `tappable` — iOS Google-only. Вывод: приблизительную область рендерить полигоном (окружность из ~64 вершин), не Circle — получаем и тап, и пунктир на iOS.
6. **Кластеризация.** Нативная кластеризация на Apple Maps вызывает runtime exception (`docs/installation.md`) — Google-SDK-only функция. Решение: кластеризация — **только JS-слой** — supercluster 9.1.0 (`getClusters(bbox, zoom)`, expansion zoom) поверх MapView; три утверждения спеки варианта кластеров — три компонента-маркера. Размер кластера 40×40 в экранных единицах соответствует — кластерный маркер это RN-вьюха, а не география.
7. **Слои.** `UrlTile` с `{x}{y}{z}` для OSM-тайлов. Внимание: OSM-серверы ограничивают бесплатное использование — для продакшна нужен свой тайл-сервер или другой источник.

## 3. Не подтверждено документацией — требует практической проверки

- Работа rnmaps 1.29 под RN 0.86 + React Compiler на реальном устройстве (peer-диапазон покрывает, но это новая комбинация).
- Сохранение центра/масштаба/фильтров при возврате из карточки: архитектурно корректно — карта лежит внутри root `Stack` (`(tabs)`), push карточки её не размонтирует; но это отдельный критерий приёмки №5 спеки — проверять в Expo Go.
- Строгость тапа Polygon и пунктира на Android.
- Перфоманс кластеризации при реальной плотности мест (десятки–сотни в регионе).
- expo-maps в Expo Go — не проверял (не нужен при рекомендованном варианте).

## 4. Риски кластеризации и приватности координат

**Приватность (критерий 6 спеки).** Архитектура: бэкенд отдаёт для приблизительных мест только публичные координаты представления (центр с точностью ~1 км); исходная точка вообще не попадает в API-ответ. Тогда клиентская кластеризация оперирует только публичными данными, и смешанный кластер не может восстановить скрытую точку по построению. Дополнительно: сервер должен округлять/шумить сами публичные координаты до сетки ~1 км, иначе точное значение центра обесценит задумку. Это архитектурное следствие спеки, не задокументированный факт — сверить с решением по бэкенду (аудит §4.1: бэкенда ещё нет).

**Кластеризация.** Риск не в supercluster (зрелый, активный), а в интеграции: пересборка кластеров на каждый `onRegionChangeComplete` и поведение `tracksViewChanges` с кастомными вьюхами. Приёмка по `code-review-and-quality` на этапе 04: ось производительности (нет горячих пересборок на каждый шаг камеры) и ось корректности (число в кластере = число мест, не отчётов — P0 спеки).

Открытые вопросы из аудита, влияющие на карту: пунктир на Android (решение дизайна), «слои» — поведение B4, геолокация — GPS или заглушка B2.

## 6. План реализации (по `incremental-implementation`)

Один slice — одно вертикальное изменение; каждый закрывается проверкой `npx tsc --noEmit` и прогоном сценария в Expo Go:

| # | Slice | Результат проверки |
|---|---|---|
| 0 | Зависимость + плагин; MapView (Apple Maps) на `(tabs)/map.tsx`, кнопки `+/−` | карта видна и зумится в Expo Go |
| 1 | Демо-точечные пины (K-DS-вьюха), тап → заглушка `/place/[id]` → назад | возврат сохраняет центр/масштаб |
| 2 | Приблизительная область ~1 км (Polygon, пунктир), тап по всему кругу → карточка | критерий 4 спеки |
| 3 | supercluster: три варианта кластеров, тап → zoom → раскрытие, число = мест | критерии 1–3 |
| 4 | Чипсы Все/Дикие/Платные, состояние фильтров переживает навигацию | критерий 5 |
| 5 | `UrlTile`-слой OSM под контролем «слои» | пункт B4 |

Первая минимальная задача в разработку — **slice 0**: установить `react-native-maps`, добавить плагин в `app.json`, отрисовать MapView с Apple Maps и кнопками `+/−` на экране-заглушке `(tabs)/map.tsx`, подтвердить в Expo Go. Критерий готовности: карта отображается и зумится в Expo Go, `npx tsc --noEmit` чист.
