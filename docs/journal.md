# Клюёт — Журнал (`journal.md`)

> Статус: спецификация MVP для реализации. 20 октября 2026.
> Связанные документы: `reports.md`, существующие продуктовые документы проекта и актуальные макеты Figma.
> Макеты: https://www.figma.com/design/WIFYiVA2QFFcDn0YYA1CCq/K?node-id=0-1

## 1. Зачем нужен журнал

Журнал — персональный раздел пользователя с двумя самостоятельными вкладками:

1. **«Мои места»** — только места, которые **создал** текущий пользователь. Это не список посещённых мест и не избранное.
2. **«Мои отчёты»** — все отчёты, которые **опубликовал** текущий пользователь, включая отчёты на местах **других авторов**.

Журнал не дублирует карточку места или детали отчёта: карточки списка ведут в соответствующие существующие экраны. **Сущности не смешивать:** место владеет координатами, платностью, типом и точностью точки; отчёт содержит сведения о рыбалке и ссылку `placeId` на место. Характеристики места могут присутствовать только в карточках/деталях места, но не становятся полями отчёта.

## 2. Сценарии и переходы

| Источник | Действие | Результат |
| --- | --- | --- |
| Навигация приложения | Открыть журнал | Последовательная работа вкладок «Мои места» / «Мои отчёты» |
| «Мои места» | Тап по карточке места | Детали выбранного места |
| «Мои отчёты» | Тап по карточке отчёта | Детали выбранного собственного отчёта |
| Детали своего отчёта | Редактировать | Форма редактирования (см. `reports.md`) |
| Детали своего отчёта | Перейти в место | Детали места, к которому он привязан |
| Пустая вкладка «Мои места» | «Добавить» | Существующий сценарий добавления места |

При возврате из дочернего экрана восстанавливать **ту же вкладку журнала и её состояние** (по возможности позицию прокрутки). После успешного редактирования карточка показывает актуальные данные. Списки должны обновляться после публикации или редактирования в других частях приложения.

## 3. «Мои места»

В карточках использовать состав информации, иерархию и визуальные состояния из Figma: название, виды рыбы, тип места, платность, точность координат, дату и прочие предусмотренные элементы.

**Дата карточки собственного места — дата создания места.** Она не изменяется при последующих правках. Дату последнего редактирования в MVP пользователям не показываем.

### Редактирование места после появления отчётов

- **Пока у места нет ни одного опубликованного отчёта**: действуют обычные существующие правила редактирования места.
- **После первого опубликованного отчёта любого пользователя**: фиксируются **координаты**, **тип места** и **платность**. Менять их нельзя, чтобы исторические отчёты оставались привязанными к тому же смыслу места.
- Исправлять название и описание допустимо (например, убрать опечатку).
- Ограничения должны проверяться **на сервере**, не только скрытием полей в интерфейсе.
- В UI нужно ясно объяснить недоступность заблокированных полей. Точный способ и текст адаптировать к существующему компоненту редактирования места; не добавлять новые масштабные сценарии без согласования.

Важно: история правок не включена в MVP. Технические поля `createdAt` / `updatedAt` могут храниться, но история версий отдельно не показывается.

## 4. «Мои отчёты»

Карточки соответствуют актуальным макетам. Поскольку автор — текущий пользователь, ключевой контекст — **результат рыбалки и название места**, а не повторение имени самого пользователя.

- Показывать дату **самой рыбалки**, не дату публикации.
- Сортировать по дате рыбалки по убыванию; при равенстве — по времени публикации.
- Отображать состояния «с уловом / без улова» и «с фото / без фото».
- Тап открывает **существующий экран деталей отчёта**, а не отдельную «журнальную» версию.
- Правила просмотра, редактирования и ошибок подробно описаны в `reports.md`.
- Удаление отчётов в MVP отсутствует.

## 5. Пустые состояния

| Вкладка | Состояние MVP | Действие |
| --- | --- | --- |
| «Мои места» | «Добавленных мест нет» | Кнопка «Добавить», ведёт в сценарий создания места |
| «Мои отчёты» | «Отчётов пока нет» | Без отдельной кнопки добавления: отчёт создаётся через выбранное место |

Пустое состояние показывается только после подтверждённой успешной загрузки пустого списка. Во время запроса — skeleton; при ошибке сети — состояние ошибки с возможностью повтора.

## 6. Загрузка, успех и ошибки

- На входе в журнал / при первоначальном получении вкладки использовать skeleton карточек, повторяющий фактическую геометрию компонентов и учитывающий светлую/тёмную тему.
- Не показывать «ничего нет», пока запрос не завершился.
- При сбое — сообщение об ошибке и «Повторить»; без бесконечного loader/skeleton.
- Успешное создание места: открыть созданное место, показать **тост «Место добавлено»** после перехода.
- Успешное редактирование места: показать **«Изменения сохранены»** после перехода к обновлённым данным.
- Успешное создание отчёта и его редактирование: тосты **«Отчёт опубликован»** / **«Изменения сохранены»** по `reports.md`.
- Один общий компонент Toast, время показа примерно три секунды; ошибки сохранения — через соответствующую модалку, не через success toast.
- Полноэкранный загрузчик используется для инициализации приложения, не для обычного переключения вкладок журнала.

## 7. Критерии приёмки MVP

- [ ] Во вкладке «Мои места» только места, созданные текущим пользователем.
- [ ] Во вкладке «Мои отчёты» все отчёты текущего пользователя, включая сделанные на чужих местах.
- [ ] Карточки открывают общие экраны места/отчёта; возврат сохраняет вкладку.
- [ ] В карточке места дата создания не меняется после редактирования.
- [ ] С первого опубликованного отчёта нельзя менять координаты, тип и платность места; название/описание редактируемы.
- [ ] Список отчётов сортируется по дате рыбалки.
- [ ] Обе пустые вкладки, загрузка и сетевые ошибки корректны.
- [ ] После добавления/редактирования данные в журнале актуализируются.
- [ ] Успешные действия показывают согласованные тосты.
- [ ] **Было → Стало:** все ранее работавшие сценарии продолжают работать.

## 8. Backlog — НЕ реализовывать в MVP

- История изменений мест (что, когда и кем изменено) с возможностью просмотра другими пользователями.
- История изменений отчётов и просмотр другими пользователями.
- Удаление собственных отчётов.
- Дополнительные сортировки, фильтры и расширенная аналитика журнала — только после проверки потребности на пользователях.
- Уточнение политики исправления существенных ошибок в месте после первого отчёта (например, отдельная процедура модерации) — после MVP.

**Правило для Claude Code:** Backlog не является заданием на текущую реализацию. Не реализовывать без отдельного согласования.

## 9. Инструкция по внедрению

Сначала изучить код, экраны, навигацию, существующие UX-правила и Figma. Не создавать второй экземпляр уже реализованных сущностей и экранов. Не менять рабочую логику прототипа без причины. При расхождениях между документом, макетами и кодом сообщить до реализации спорной ветки. Использовать текущие компоненты и токены, проверить все критерии приёмки и регрессию.
